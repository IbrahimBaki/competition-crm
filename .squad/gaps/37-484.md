# Gaps — Story 37 (FE-07): Reports, Dashboards and Customer Portal

## 1. ReportDefinitionResource missing filter descriptors and title

**Symptom:** `frontend/src/features/reports/types.ts` cannot be built as specified; the plan calls for `ReportDefinition.title` and `ReportFilterDescriptor[]`, but the API exposes neither.

**Evidence:** `app/Domains/Reporting/Http/Resources/ReportDefinitionResource.php:17-21` returns only `[key, permission, columns]`. The interface `ReportDefinition` (lines 10-39) defines only `key()`, `permission()`, and `columns()` — no title or filter descriptor accessor.

**Impact:** Cannot render report titles from the API; must derive from i18n keys (`reports.<key>.title`). Cannot derive per-report filter sets from the resource; must use a single global filter descriptor constant derived from `ReportQueryRequest.php:25-39` instead. The plan's task 1 calling for "Shape these fields against the real payloads" is impossible.

**Workaround:** 
- Use `features/reports/filters/descriptors.ts` as a module-level constant mirroring `ReportQueryRequest::rules()` — all reports accept the same 11 filters (date_from, date_to, timezone, branch, department, team, agent, category, priority, channel, tag).
- Resolve report titles via a `reports.<key>.title` i18n key; the API-provided `key` maps to the i18n lookup.
- Column labels also derive from i18n: `reports.<key>.column.<columnKey>.label` and `reports.<key>.column.<columnKey>.numeric` (boolean).

**Suggested fix:** Expose `filters()` and `title()` methods on `ReportDefinition`, and have `ReportDefinitionResource` return them serialized with bilingual support. For now, the frontend layer absorbs the gap.

## 2. ReportResult columns lack label and numeric metadata

**Symptom:** `ReportResultTable` cannot determine column alignment (LTR numeric columns right-align, RTL mirrored). The plan's proposed types include `{key, label, numeric}`, but the API returns only `list<string>` column keys.

**Evidence:** `ReportResultResource.php:14-23` returns `{generated_at, timezone, rows, totals}` — no column metadata. `ReportDefinition::columns()` returns `list<string>` (line 30).

**Impact:** Column labels and alignment intent must come from i18n configuration, not the API.

**Workaround:** 
- Column labels: `reports.<key>.column.<columnKey>.label` 
- Numeric flag: `reports.<key>.column.<columnKey>.numeric` (boolean)
- `ReportResultTable` reads these from i18n at render time.

**Suggested fix:** Extend `ReportDefinition` to expose `columnDescriptors(): array<{key, label, numeric}>` or add a `Report` resource DTO that wraps definition + metadata.

## 3. No export-status read route for async report exports

**Symptom:** Export workflow is broken for large reports. `ReportExportController::store` returns 202 (Pending) for reports exceeding `config('reporting.export.sync_rows')`, with `{id, state, row_count}`, but there is **no route** to fetch status or download the finished file.

**Evidence:** `app/Domains/Reporting/Http/Controllers/ReportExportController.php:52-83`: rows ≤ sync threshold → return file (200); rows > sync threshold → create record in Pending state, dispatch job, return 202 with `{id, state}`. `routes/api.php:342-347`: only `GET reports`, `GET reports/{report}`, `POST reports/{report}/export` exist. No `GET reports/exports/{exportId}` or equivalent.

**Impact:** Frontend cannot poll for export completion or retrieve the file after generation. The feature is broken for any report exceeding the sync threshold. UI must treat export as fire-and-forget acknowledgement only, or be stubbed as "not yet available".

**Workaround:** 
- Drop polling logic. 
- Treat `202 Accepted` as terminal acknowledgement ("Your export is being prepared and will be emailed to you" or similar placeholder message).
- If a file is returned synchronously (200), download it immediately.
- Log in comment: `TODO(gap-484): No export status/download route. Export UI is acknowledgement-only for async exports.`

**Suggested fix:** Add routes:
- `GET reports/exports/{exportId}` → return `{id, state, download_url?, expires_at, error?}`
- Optionally: `DELETE reports/exports/{exportId}` for cleanup, `GET reports/exports` to list pending.

Or implement signed download URLs that can be sent via email without the route.

## 4. No portal attachment upload route

**Symptom:** Task 8 assumes the portal ticket submit form can attach files via `features/shared/attachments/AttachmentUploader.tsx`, but the portal API has no upload endpoint.

**Evidence:** `routes/api.php:126-150` (portal routes). Only `GET attachments/{attachment}` at line 150 (PortalAttachmentController::show). No `POST attachments` or portal-scoped upload route. Internal staff API has `POST attachments` at line 153 (staff-only, behind `auth:sanctum`).

**Impact:** Portal users cannot upload attachments when submitting a request.

**Workaround:** 
- Drop the `AttachmentUploader` from `PortalTicketNewPage`.
- Submit form accepts only text (subject/description).
- Log in component: `TODO(gap-484): No portal attachment upload route.`

**Suggested fix:** Add route `POST v1/portal/tickets/{ticket}/attachments` backed by a portal-scoped controller that enforces the same visibility checks as `PortalTicketScope`.
