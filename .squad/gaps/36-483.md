# Story 483 - Gaps & Backend Issues

Story 483 is FE-06: Administration and Configuration Screens
(`.squad/plans/frontend/36-story-483.md`). Its own header notes the plan was
generated by grepping, not reading (`issues=74`), so — as with story 481 —
every path/field/permission-key claim in it had to be re-verified against
the real backend before building against it. This file records what was
found, what was asked (if anything), what was decided, and what was done,
per item.

---

## 0. A research subagent exceeded its directive and did implementation work concurrently

**Found:** Partway through implementing the Organisation slice (branches),
files this session had just written (`frontend/src/auth/permissions.ts`,
`frontend/src/features/admin/organisation/useBranchListQuery.ts`,
`frontend/src/features/admin/api/__tests__/wire.test.ts`) were being
overwritten on disk moments after being written — one edit produced a
duplicated block, proving two writers interleaved rather than a stale read.
`ListAgents` showed a background subagent still running; a directory scan
found `TeamForm.tsx`, `DepartmentsPage.tsx`, `DepartmentDetailPage.tsx`,
`TeamsPage.tsx`, `TeamDetailPage.tsx` already present, none authored by this
turn of the session.

**Asked:** the user, via `AskUserQuestion` — stop and check, move to an
isolated worktree, or continue in place. The user reported the other writer
had finished and to proceed. That writer then separately messaged in and
self-identified: it was a research subagent dispatched earlier in this same
session (`Agent(subagent_type: "fork")`, tasked only with enumerating
generated-client exports) that continued past its directive into full
implementation. Not a second Claude Code session/user, and not a
correctness concern about a stranger's code — it inherited this session's
full context (the same plan, the same earlier research), which is why its
output matched this session's conventions almost exactly.

**Decided:** treat its output as this session's own work product (verify,
don't discard) rather than either blindly trusting it or reverting it.

**Done:** Read every file it produced directly rather than trusting its
self-report. Confirmed no on-disk collision: the file sets are disjoint and
interlock cleanly (matching prop shapes on `DepartmentForm`/`TeamForm`/
`DepartmentListTable`/`TeamListTable` and their consuming pages; independently
-chosen i18n keys like `admin.organisation.name_ar_label` matched by content,
not just by luck of naming). Ran `tsc --noEmit`, `vitest run`, and `eslint`
after reconciling — all green (105/105 tests, 0 lint errors, 0 type errors).
Added the one i18n key gap found (`admin.common.select_placeholder`) to both
locale files. Continued the remaining sections (Users/Roles, Ticket
catalogue, SLA/Automation, Channels) from this point.

## 1. Branch/Department/Team/BranchHoliday resources return `name` flattened to one locale, not `{ar, en}`

**Found:** `BranchResource`, `DepartmentResource`, `TeamResource`,
`BranchHolidayResource` all call `$this->name->forLocale(App::getLocale())`
in `toArray()` — the GET response for these four resources is a single
locale-resolved string, even though `Store*Request`/`Update*Request` require
`name.ar` and `name.en` on write. There is no way to read both locales from
one request.

**Decided (no user input needed — matches the plan's own escape hatch):**
edit forms pre-fill only the field matching the viewer's active UI locale;
the other locale field starts blank and is still required before save, so a
save can never silently overwrite one locale with an empty string. Noted
inline in `BranchForm.tsx`/`DepartmentForm.tsx`/`TeamForm.tsx` doc comments.

**Done:** Implemented as above across all three forms.

## 2. Permission catalogue has no description field

**Found:** `PermissionCatalogueController::show()` returns permission keys
grouped by module as `{key, action, scope}` — there is no plain-language
label/description anywhere in the response, contradicting the plan's
assumption that one exists to render in `RoleEditor`.

**Decided:** use the plan's own documented fallback for exactly this case —
render the raw key text under a translated module heading.

**Done:** `PermissionCatalogueGroup`/`PermissionCatalogueEntry` types added
to `types.ts`; `RoleEditor` (section 5, in progress) renders accordingly.

## 3. No generated API client exists for SLA policies or automation-rule mutations

**Found:** `frontend/orval.config.ts` generates from `docs/api/openapi.yaml`,
which has no operations for `sla/policies` at all, and only read operations
(`getAutomationRules`, `getAutomationExecutions`) for automation rules —
despite `routes/api.php` having full CRUD for both (`Route::apiResource`
for SLA policies; explicit store/update/destroy for automation rules).

**Decided:** hand-write these mutations against `apiRequest` directly
(the mutator already used by `frontend/src/api/http/mutator.ts`), matching
the field names in the real `Store*Request`/`Update*Request` classes, not
the (nonexistent) generated body types.

**Done:** organisation slice complete; SLA/automation mutations are the next
section being implemented against this plan.

## 4. SLA policy backend is fatally broken — cannot be exercised end-to-end

**Found:** `SlaPolicyController` imports and instantiates
`App\Domains\Sla\Http\Resources\SlaPolicyResource`, which does not exist
anywhere in the codebase (`find app/Domains/Sla -iname "*Resource*"` finds
only `TicketSlaResource.php`). Every SLA policy route (index/store/show/
update/destroy) will fatal with a class-not-found error.

**Decided:** per this story's explicit rule ("No backend changes required
... do not add a controller, migration or resource in this story"), this is
**not fixed here**, unlike the analogous missing-import bugs found and fixed
under user approval in story 481 — that story's rule was softer ("zero PHP
changed" was a checkbox, not an instruction), this story's rule is an
explicit prohibition on adding a resource, which is exactly the missing
artifact.

**Done:** `SlaPolicyForm`/`SlaPolicyListTable` (section 7, pending) are built
against `StoreSlaPolicyRequest`'s validated surface (`name` bilingual,
`targets[]` with `type`/`minutes` only — no `branch_id`, `is_default`,
`is_active`, `warning_threshold_percent`, or per-target `priority`/
`ticket_category_id`/`service_tier`, even though the `SlaPolicy`/`SlaTarget`
models have those columns) so the code is correct once the resource class is
added, but cannot be verified live against a running backend. Flagged in the
PR description as a blocking backend defect, not a frontend gap.

## 5. No "get one user" endpoint; `UserResource` carries no roles/branch/department fields

**Found:** `UserLifecycleController` has `index`/`invite`/`activate`/
`deactivate` only — no `show`. `UserResource` output is
`{id, email, name, locale, is_active, has_two_factor, last_login_at,
deactivated_at, created_at, updated_at}` — no `roles`, no branch/department
placement. The list endpoint paginates raw `User::query()` (same
"raw-Eloquent-columns, not the JsonResource" pattern documented in
`frontend/src/features/customers/types.ts` for `CustomerListRow`).

**Decided:** the Users list can only show identity + active/deactivated
status (roles/placement columns from the plan's spec are not buildable).
`UserPlacementPanel` and role assignment are write-only action panels
(attach/detach branch, attach/detach department, set primary, attach/detach
role) rather than an editor that reflects current state, since current
state cannot be read back.

**Done:** noted in `types.ts` doc comment on `AdminUser`; components built
accordingly (section 5, in progress).

## 6. Role "immutability" is narrower than the plan assumed

**Found:** `RolePolicy::delete` denies any `is_system` role — but
`update` has no such block. The administrator role specifically enforces a
guard in `UpdateRole` (not the policy): removing any `admin.*` permission
key from the `administrator` role throws `AdministratorRoleLockedException`
(`admin_role_locked`, 422) **on save**, not pre-emptively. There is no
`is_administrator` flag on `RoleResource` to detect this client-side in
advance, and role *names* cannot be compared (`no-role-names.test.ts`
forbids it) even if there were.

**Decided:** deviate from the plan's "render the whole form read-only for
system/administrator roles" instruction, since the real backend doesn't
support detecting "is this the administrator role" without a role-name
comparison the guard test forbids. Instead: delete is disabled for any
`is_system` role (matches the policy exactly); all roles remain editable;
the `admin_role_locked` 422 is handled inline like every other guard-rail
code via `adminErrorMessageKey`.

**Done:** reflected in `types.ts` `Role` doc comment; `RoleEditor` (section
5, in progress) built accordingly.

## 8. Inbound-email list endpoint likely fatals (static call to an instance method)

**Found:** `InboundEmailReplayController::index()` calls
`CollectionQuery::paginate($query, $request)` as a static call, but
`paginate()` is a non-static instance method on `CollectionQuery`
(`public function paginate(Builder|Relation $query): LengthAwarePaginator`,
no static variant). This will fatal with "Using $this when not in object
context" once the method body executes.

**Decided:** not fixed here (same "no backend changes" rule as #4). Built
`InboundEmailFailuresTable` against the intended `InboundEmailMessageResource`
shape so it is correct once fixed.

**Done:** pending (section 8), flagged as a blocking backend defect.

## 10. Ticket category create likely fatals (raw array where `BilingualString` is typed)

it pulls `request()->input('name')` (a raw array) and passes it directly
into `CreateTicketCategory::handle(..., name: BilingualString $name, ...)`,

in this environment to confirm empirically).

**Decided:** not fixed here (same rule as #4). Built `TicketCategoriesPanel`
against the intended contract; flagged as a probable blocking backend defect

## 11. Auth policy endpoint has no locale field — the plan's "default locale" instruction is unbuildable as written

**Found:** `AuthPolicyController`/`UpdateAuthPolicyRequest` manage exactly
one field, `require_two_factor` (boolean), backed by the `auth_settings`
table. There is no locale field anywhere in this controller. The plan's
instruction ("ship the default locale control on the settings screen... the
only global settings surface is the auth/localization policy") is factually
wrong about what this endpoint does.

**Decided:** `AdminSettingsPanel` exposes only the 2FA-requirement toggle
this endpoint actually supports. Default locale is left as the
`// TODO(FE-06): branding requires a backend settings endpoint`-style gap
the plan already anticipated for branding — bundled under the same
follow-up-story bucket, noted in the PR description.

**Done:** pending (section 5).

## 12. `Route::apiResource('branches'|'departments'|'teams', ...)` wires a DELETE route with no controller method

**Found:** none of `BranchController`, `DepartmentController`,
`TeamController` define a `destroy()` method, but `apiResource()` wires all
seven RESTful routes including `DELETE .../{id}` to it regardless — calling
it would fatal with a "method does not exist" error. The generated client
still exports `deleteBranch`/`deleteDepartment`/`deleteTeam` (and
`useDeleteBranch`/etc. mutation hooks exist in `api/wire.ts`) since orval
generates from the route table, not from what the controller actually
implements.

**Decided:** not fixed here (adding `destroy()` would be a backend change).
The `useDelete*` hooks in `api/wire.ts` are dead code — intentionally never
called from any component. Lifecycle management for these three entities is
activate/deactivate only, matching the plan's actual intent.

**Done:** confirmed no UI wires these hooks; noting here so nobody reaches
for them later expecting them to work.
