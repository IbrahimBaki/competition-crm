# Story 459 — Implementation Notes

## Issues Discovered and Resolved

### 1. Migration Index Name Length
**Issue:** The unique constraint name on `customer_duplicate_candidates(customer_id, duplicate_customer_id)` exceeded MySQL's 64-character identifier limit.

**Root Cause:** Laravel's automatic naming convention produces names like `customer_duplicate_candidates_customer_id_duplicate_customer_id_unique` (79 chars).

**Resolution:** Explicitly named the index as `dup_cand_pair_unique` (21 chars) and the status index as `dup_cand_status_created` in migration 090100.

### 2. Phone Normalization Tests Required Correction
**Issue:** Initial test expectations assumed leading zeros would be preserved in E.164 format (e.g., `+9660501234567`).

**Root Cause:** Misunderstanding of E.164 standard which strips trunk prefixes (leading 0 in Saudi format).

**Resolution:** Updated tests to expect correct E.164 format:
- `0501234567` → `+966501234567` (leading 0 stripped, country code added)
- `00966501234567` → `+966501234567` (leading 00 stripped, replaced with +)
- `+966501234567` → `+966501234567` (no change, already E.164)

### 3. Phone Normalization Logic Bug
**Issue:** Country code was being applied incorrectly, doubling in some cases (e.g., `00966501234567` → `+966966501234567`).

**Root Cause:** The logic was treating the `00` case (international without +) and the `0` case (domestic) identically, both adding the country code.

**Resolution:** Differentiated the handling:
- `00XXX...` format: strip `00`, add `+` directly (number already includes country code)
- `0XXX...` format: strip `0`, add `+{country_code}` (domestic format needs code added)
