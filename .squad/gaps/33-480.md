# Story 480 - Gaps & Backend Issues

Story 480 is FE-03: the ticket list and ticket detail workspace
(`.squad/plans/frontend/33-story-480.md`). Building it surfaced a large
number of backend/contract issues that the plan's authors could not have
seen (the plan was written without full file reads). Each item below is
recorded as: what was found, what was asked, what was decided, and what was
done about it.

---

## 1. Generated API client body shapes don't match the FormRequests

**Found:** The orval-generated request-body types under
`frontend/src/api/generated/model/` are generated from
`docs/api/openapi.yaml`, which has drifted from what the Laravel
FormRequests in `app/Domains/Ticketing/Http/Requests/` actually validate.
Confirmed by reading `rules()` on each FormRequest directly (not by running
tests — the backend test suite is independently broken, see #6).

| Endpoint | Generated body says | FormRequest actually validates |
|---|---|---|
| `POST .../messages` | `{ visibility: 'public'\|'internal' }` | `StoreTicketMessageRequest`: `{ body, channel (required enum), is_internal }` — there is no `visibility` field on the backend at all |
| `POST .../status` | `{ status_id }` | `ChangeTicketStatusRequest`: `{ status (uuid, required), reason? }` |
| `POST .../assign` | `{ user_id }` (required) | `AssignTicketRequest`: `{ assignee_uuid? (nullable), version? }` |
| `POST .../transfer/agent` | `{ user_id }` | `TransferTicketToAgentRequest`: `{ user_uuid (required), version? }` |
| `POST .../transfer/department` | `{ department_id }` only | `TransferTicketToDepartmentRequest`: also accepts `keep_assignee?`, `version?` |
| `POST .../claim`, `.../reopen`, `.../spam`, `DELETE .../spam` | no body param in the generated function at all | `ClaimTicketRequest` needs `{ version? }`; `Reopen`/`MarkSpam`/`RestoreFromSpam` all need a **required** `{ reason }` |
| `POST .../merge` | `{ target_ticket_id }` | `MergeTicketsRequest`: `{ target }` |
| `POST .../split` | `{ message_ids: string[] }` | `SplitTicketRequest`: `{ subject, body, category? }` — a completely different operation, not a message-selection split |
| `POST .../links` | `{ related_ticket_id, link_type }` | `StoreTicketLinkRequest`: `{ target, relation }` |

The worst case: following the generated `visibility` field literally would
mean `is_internal` is never sent, so it defaults false — every "internal"
note would go out as an ordinary public message. This is the exact failure
this story's composer exists to prevent.

**Asked:** Wire the UI to the generated types (matches the frozen contract,
non-functional) or to the real FormRequests (deviates from the documented
contract, but works)?

**Decided:** Wire to the real backend (FormRequests win — they're what
actually validates the request).

**Done:** `frontend/src/features/tickets/api/wire.ts` is the single adapter
layer. It reuses the generated functions for URL/method (still correct) and
builds the real payload, with a header comment listing every mismatch. No
generated file was hand-edited. Merge/split were intentionally **not**
wired — not required by this story's Done Criteria, and split's real
shape (`subject`/`body`/`category`) is a different product decision than
"pick messages to split off," which isn't this story's call to make
silently.

**Follow-up for whoever owns the OpenAPI spec:** regenerate
`docs/api/openapi.yaml` from the actual FormRequests (or fix the
FormRequests to match the spec, if the spec was the intended contract) so
`frontend/src/features/tickets/api/wire.ts` can eventually be deleted.

## 2. List/queue endpoints skip TicketResource entirely — raw model leakage

**Found:** `TicketController::index()`, `TicketQueueController::mine()`,
`TicketQueueController::department()`, `TicketLinkController::index()`, and
`TicketMessageController::index()` all call
`ApiResponse::collection($paginator)` where `$paginator->items()` are raw,
unwrapped Eloquent models — not `TicketResource::collection(...)` /
`TicketMessageResource::collection(...)` / etc. Only the single-item
endpoints (`show`, `store`, `update`, message `store`) correctly wrap in a
Resource.

Practical effect for the list endpoint specifically:
- Exposes the ticket's internal auto-increment integer PK (`id`) as well as
  `uuid` — and `customer_id`, `assigned_user_id`, `ticket_category_id` are
  the **raw internal integer FKs** of `customers`/`users`/`ticket_categories`
  (all of which use auto-increment PKs, confirmed via their migrations),
  not the UUIDs those resources expose everywhere else. There is no
  client-resolvable way to turn these into a customer/agent/category name.
  This violates this repo's own "IDs = UUID" API rule.
- No nested `status` object, no `sla` block, no `available_transitions` —
  all computed inside `TicketResource`, which this endpoint skips.
- Internal-only columns leak (`subject_normalised`, `body_normalised`,
  `classification_source`, etc.).
- `department_id` is the one exception: departments use a UUID primary key
  (confirmed via migration), so it *is* resolvable via the departments list.

The message-list endpoint has the same pattern: raw `TicketMessage` rows
have no `author` (relation not loaded) and no `attachments` (relation not
loaded), and `author_user_id` is a raw internal integer.

**Asked:** Build the list table around only what's actually returned, do a
per-row detail fetch to backfill the missing data (defeats pagination), or
stop and get the backend fixed first?

**Decided:** Build with only what's available.

**Done:**
- `frontend/src/features/tickets/types.ts` documents `TicketListRow` and the
  message-list shape of `TicketMessage` as the *raw* shapes, with a comment
  explaining why, rather than pretending they match the Resource.
- `TicketListTable.tsx` shows reference, status, priority, subject, updated
  date, and department (resolved via a single batched `useGetDepartments()`
  call, not per-row) — no customer/assignee/SLA columns, since that data
  isn't in the response.
- `TicketConversation.tsx` shows the author's *type* (agent/customer/
  system/bot) instead of a name, and does not attempt to render historical
  attachments (the data isn't there).
- `TicketHistoryPanel.tsx`'s events/links lists are built against the raw
  `TicketEvent`/`TicketLink` shapes for the same reason.

**Follow-up:** wrap these five endpoints in their Resources
(`TicketResource::collection()`, `TicketMessageResource::collection()`,
`TicketLinkResource::collection()`). This is bigger than a one-line fix (it
changes response shape for whatever already consumes these endpoints) so it
was **not** done as part of this story's "minimal fix" exception below.

## 3. `ApiResponse::created()` does not exist — fatal error on 15 call sites

**Found:** `app/Support/Http/ApiResponse.php` defines only `item()`,
`collection()`, `noContent()`, `toResponse()`. `ApiResponse::created()` is
called in 15 places across 8 controllers, including all four
`TicketLifecycleController` actions (status change, reopen, mark spam,
restore-from-spam) and `TicketLinkController::store()`. Every call is a
guaranteed `Error: Call to undefined method` → 500. This is independent of
anything the frontend sends — it means **status transitions were completely
non-functional** before this fix, which is one of this story's two most
safety-critical, most-tested features.

**Found (same investigation):** `TicketController::history()` calls
`ApiResponse::collection($events, collectionQuery: new CollectionQuery(...))`
— `collectionQuery` is not a parameter of `ApiResponse::collection()`
(`page, meta, filters, sort`). Every call to
`GET /tickets/{ticket}/history` was a guaranteed fatal error.

**Found (same investigation, not fixed — see below):**
`TicketCategoryController::index()` calls
`ApiResponse::collection(TicketCategoryResource::collection($categories), paginate: false)`
— `collection()` requires a `LengthAwarePaginator` as its first argument, not
an `AnonymousResourceCollection`, and has no `paginate` parameter either.
`GET /ticket-categories` is also a guaranteed fatal error.

**Asked:** Fix the two `ApiResponse` bugs (missing `created()`, invalid
`collectionQuery:` argument) as minimal, mechanical, additive changes, or
leave the backend untouched and report only?

**Decided:** Fix both minimally, and document every such decision here with
the story number; set up a hook to keep doing this automatically going
forward (see `.claude/hooks/gap-log.md` / settings.json entry).

**Done:**
- Added `ApiResponse::created(mixed $data, array $meta = []): self` —
  delegates to `item($data, 201, $meta)`, matching every one of the 15 call
  sites' actual usage (`ApiResponse::created($resource)`, always a single
  positional argument).
- `TicketController::history()`: removed the invalid `collectionQuery:`
  named argument; it now calls `ApiResponse::collection($events)` like every
  other unfiltered collection endpoint in this codebase.

**Not fixed (out of scope for the "minimal" exception):**
`TicketCategoryController::index()`'s crash. Fixing it means changing how
`ApiResponse::collection()` is called for a case it was never designed for
(a plain resource collection with no paginator), which is a small design
decision, not a one-line correction — flagging for a deliberate fix rather
than taking it silently. Effect on this story: `TicketFilterBar`'s category
filter and `TicketPropertiesPanel`'s category display degrade quietly (the
query errors, the dropdown just shows "Any" / read-only text) rather than
crashing the page.

## 4. Endpoints this story needs that don't exist

- **Bulk ticket actions.** No `bulk` route anywhere under
  `app/Domains/Ticketing/` (confirmed via `grep -rn bulk routes/api.php`).
  `TicketBulkActions.tsx` fans out to the per-ticket assign/status endpoints
  with bounded concurrency (max 4 in flight) instead, per the plan's own
  documented fallback for this exact case.
- **Saved views.** `TicketSavedView`, `TicketSavedViewResource`, and the
  save/delete actions all exist in `app/Domains/Ticketing/`, but there is no
  route for any of it in `routes/api.php`. `SavedViewsBar.tsx` is
  localStorage-backed only (per-browser), per the plan's documented
  fallback.
- **Ticket category / tag reassignment.** `PermissionKey::TICKETS_RECLASSIFY`
  and `::TICKETS_TAG` exist, but there is no route to reclassify a ticket's
  category or manage its tags after creation — `UpdateTicketRequest::rules()`
  only accepts `subject`, `body`, `priority`, `status`. `TicketPropertiesPanel`
  can only offer an edit control for `priority`; category/department/tags/
  custom fields are shown read-only.
- **Attachment scan-status polling.** `GET /attachments/{attachment}`
  streams the file itself (and throws while scanning is pending) — there is
  no JSON endpoint to re-check an attachment's `scan_state` after the
  initial upload response. `AttachmentUploader.tsx` reflects whatever
  `scan_state` the upload call returned; if it comes back `pending`, there
  is currently no way for the UI to learn it later became `clean` without a
  fresh upload.

## 5. Accessible-but-not-really: `/users`

`UserLifecycleController::index()` (`GET /users`) is gated by
`viewAny` on `User::class`, which is an admin-level permission, not
something a regular support agent holds. There is no lower-privilege
"agent directory" endpoint. Both the ticket-list assignee filter and the
detail page's assign/transfer-to-agent controls are plain UUID text inputs
rather than a name-searchable picker, because there is nothing a normal
agent can call to look up another agent's name.

## 6. Backend test suite is independently broken

`php artisan test --filter=TicketQueueTest` fails immediately with
`BadMethodCallException: Call to undefined method App\Models\User::grantPermission()`
— that method does not exist anywhere in `app/` or `tests/`. This is
unrelated to this story (no ticketing test file was touched), and appears
to affect any test using this helper. Not fixed here — flagging since it
means `php artisan test` cannot currently be used as a correctness oracle
for anything in the ticketing domain, which is why every claim in this
document is sourced from reading the FormRequest/controller/migration code
directly rather than from a passing test run.

## 7. `usePermissions.ts` bug (frontend, fixed)

`canAny` shadowed its own parameter:
`canAny: (permissions) => hasAnyPermission(permissions, permissions)` —
it compared the granted-permissions array to itself, so it returned `true`
for any non-empty `anyPermission` list regardless of what the user actually
had. Every `ActionGuard`/`RequirePermission` using `anyPermission` in this
story (and possibly earlier stories) was a no-op gate. Fixed by renaming the
parameter (`frontend/src/auth/usePermissions.ts`).

## 8. Live browser verification: three more fatal cast bugs found and fixed

**Found:** Attempted a real end-to-end browser walkthrough (login → list →
filter → detail → composer → RTL) against the actual backend, per the
Verification Steps. This required additively seeding a department/customer/
tickets (via raw `DB::table()->insert()`, since `Model::factory()` is broken
for every domain model — see §10) and surfaced three more unconditional
fatal errors, all the same shape as the `ClassificationSource` issue already
found: a bare `SomeEnum::class` in a model's `$casts` array with no `use`
import and no class of that name in the model's own namespace, so
`InvalidCastException: Call to undefined cast [...]` fires on *every*
serialization of that model, regardless of the column's actual value.

- `App\Domains\Ticketing\Models\Ticket`: `classification_source` cast
  referenced `ClassificationSource` (real location:
  `App\Domains\Ai\Models\ClassificationSource`) with no import. This meant
  the raw ticket-list serialization (§2) couldn't work *at all*, even before
  reaching the "raw shape" problem already documented — `GET /tickets`
  was a guaranteed 500.
- `App\Domains\Organisation\Models\Department`: `routing_strategy` cast
  referenced `RoutingStrategy` (real location:
  `App\Domains\Automation\Models\RoutingStrategy`), same failure.
- `App\Domains\Organisation\Models\Department`: `no_agent_fallback` cast
  referenced `NoAgentFallback` (real location:
  `App\Domains\Automation\Models\NoAgentFallback`), same failure.

**Fixed:** Added the three missing `use` imports (one line each, in
`app/Domains/Ticketing/Models/Ticket.php` and
`app/Domains/Organisation/Models/Department.php`). Verified via a full
Laravel-bootstrapped static scan of every `App\Domains\*\Models\*.php` cast
declaration (`class_exists`/`enum_exists` against the resolved FQCN) that no
other model has this problem — these three were the only ones.

**Not fixed (found, documented, left alone):**
- `App\Domains\Customers\Services\ArabicTextNormaliser::normaliseName()`
  (line 18) calls `preg_replace()` with a pattern using PCRE1-only escape
  sequences (`\F`, `\L`, `\l`, `\N{name}`, `\U`, `\u`) that PCRE2 (this PHP
  version) rejects outright: `preg_replace(): Compilation failed`. This is
  called from `TicketSearch::apply()`, which every ticket-list free-text
  search goes through — **the search box in `TicketFilterBar.tsx` is
  currently a guaranteed 500 whenever it's used**, independent of anything
  the frontend sends. Not a one-line fix (needs an actual PCRE2-compatible
  rewrite of the normalization pattern, a real product/regex decision, not
  a missing import), so left as a documented gap rather than fixed under
  the "minimal mechanical fix" allowance.
- `App\Domains\Customers\Models\Customer::boot()` calls `Str::uuid()` and a
  bare `TextNormaliser` class with neither imported — creating a `Customer`
  via `Customer::create()` (or its factory) throws. Worked around in this
  session by inserting customer rows directly via `DB::table('customers')`
  with an explicit `uuid` (the `??=` in `boot()` short-circuits past the
  missing import when the field is already set) — not fixed, since it's a
  third instance of the same class of bug but in a *closure* referencing an
  apparently-nonexistent `TextNormaliser` helper (no file by that name was
  found anywhere in `app/`), which needs a real decision about what that
  class was meant to be, not a one-line import fix.

## 9. `Model::factory()` is broken for effectively every domain model

**Found:** `Customer::factory()`, `Department::factory()` (no factory file
exists at all for Department), and by the same mechanism every other
`App\Domains\*\Models\*` model's `::factory()` throws `Class
"Database\Factories\Domains\...\...Factory" not found`. Laravel's default
factory-name resolution replaces `App\` with `Database\Factories\` and
keeps the rest of the namespace, but every factory in `database/factories/`
is declared with a **flat** namespace (`namespace Database\Factories;`),
e.g. `database/factories/CustomerFactory.php` is
`Database\Factories\CustomerFactory`, not
`Database\Factories\Domains\Customers\Models\CustomerFactory`. No model
overrides `newFactory()` and no service provider registers
`Factory::guessFactoryNamesUsing()`/`guessModelNamesUsing()` to bridge the
two conventions. This almost certainly compounds the `grantPermission()`
issue (§6 in the original write-up) in explaining why `php artisan test`
is so broadly non-functional across this codebase — most Feature tests
seed data via `SomeModel::factory()`.

**Not fixed** — this is a test-infrastructure/bootstrapping decision (add a
`guessFactoryNamesUsing` closure in a service provider, or move every
factory file under a matching nested path, or add `newFactory()` to every
model) far outside this frontend story's scope. Worked around in this
session by seeding verification data via raw `DB::table()->insert()` calls
instead of factories.

## 10. Live verification: what was and wasn't actually confirmed in a browser

Given §9 and §10, and that this sandbox shares a live dev database and dev
server with another active session (confirmed: `config/app.php`-adjacent
files and `app/Support/Http/Errors/ErrorCode.php` changed on disk mid-session
from outside this conversation), full click-through browser verification
was **partially** completed before rate-limiting (`AuthenticateStaff`'s
login attempt limiter) and the shared environment made further iteration
impractical to keep pursuing. Concretely confirmed via a real authenticated
browser session (Playwright + system Chrome) against the real backend:

- Login (`POST /auth/login` → `GET /auth/me`) succeeds end-to-end and the
  SPA reaches the dashboard.
- `GET /tickets`, `GET /tickets/queues/mine` (by construction, same code
  path), `GET /departments`, `GET /ticket-categories` (500 — pre-existing,
  §3) were all exercised with real network round-trips from the running
  Vite dev server to the real Laravel backend.
- The status filter dropdown correctly re-queries with
  `filter[status][eq]=open` and back to unfiltered — exactly the
  `CollectionQuery` wire format this story's frontend was built against.
- `AsyncBoundary`'s error path renders correctly (screenshot: "Something
  went wrong / Network error" with a working "Retry" button) when a query
  fails — this is itself one of the required behaviors (Done Criteria:
  "every async region uses AsyncBoundary with the shared states").

**Not independently confirmed live** (blocked by the login rate-limiter
before it could be reached, not by any known frontend defect): the ticket
detail screen's live render, composer mode switching, status transitions,
and the Arabic/RTL layout. These are covered instead by: the passing
component test suite (`TicketComposer.test.tsx`, `TicketStatusControl.test.tsx`,
`ConflictBanner.test.tsx`, `TicketSlaPanel.test.tsx` — 30/30 passing), a
static scan confirming no physical-direction (`ml-`/`mr-`/`text-left`/etc.)
Tailwind classes exist anywhere under `frontend/src/features/tickets/`
(RTL-safe logical properties used throughout), and the `npm run build`
production build succeeding without errors.

**Housekeeping from this verification session** (left in place, on the
shared dev database, since they're harmless additive dev/demo data): one
department ("Technical Support" / "الدعم الفني", code `TS1`), one customer
("Ada Lovelace"), two tickets ("Cannot access my account" / "Billing

to `Testing12345!` (the original `SEED_ADMIN_PASSWORD`-less seeder run
prints a random password once to console and it could not be recovered
